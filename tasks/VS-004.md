## 1. Proposed outcome and boundaries

Demonstrate one explicit offline feedback loop:

`pinned context → candidates → estimates → ranked decision or abstain →
trusted automatic priority publication → authoritative ready-set check →
recorded relevance/replanning check → atomic claim on explicit dispatch →
fixed worker → reuse ranking or compute a new decision when justified`.

Recommendations affect order among already-admitted eligible tasks only.
They cannot add/approve/import/retry work, change dependencies, choose code,
activate graph baselines, validate evidence or trigger unattended execution.
Only the trusted dispatcher performs the ordinary pending→running transition.

Use Python 3.11+, SQLite, existing dependencies and the fixed `demo_mean` worker.
Keep single-study, single-host, one-active-run behavior. No general agent
framework, live provider, trained scientific-impact predictor, event loop,
multi-resource scheduler, monitoring or public Research Manager CLI.

## 3. Minimal responsibilities and data contracts

Use small typed records and pure estimator/policy functions. Keep trusted
persistence and execution separate. These are proposed internal interfaces,
not new executable workers or commands. Algorithm identity includes name,
version, exact configuration and an implementation/source identifier; replay
must not substitute a newer implementation.

### Context

`DecisionContextV1` binds study ID and immutable charter hash and contains:

- Selected graph view, exact Q/H/C revision pins, link revisions, graph sequence,
  relevant T/R/E/B references and active baselines visible in that view.
- Selection/query version, root/filters, limits, intentional omissions, frontier,
  `portfolio_completeness=partial`, and `selection_complete = not truncated`.
  This last flag describes the declared query only, not scientific completeness.
- Complete canonical VS-002 execution snapshot bytes/hash, including charter
  bytes, tasks/dependencies/statuses, run outcomes/costs and unvalidated evidence.
- Optional versioned **revealed synthetic feedback** with fixture source, payload
  hash and revealing run/evidence links where applicable; no unrevealed oracle.
- Trusted installed dispatch-profile identity/hash. Capture time is metadata
  outside content identity so identical input bytes can deduplicate.

Capture graph and execution in **one caller-owned read transaction**. Extract
only a private transaction-owned graph read body; retain the existing public
graph read wrappers and their nesting refusal. `PlanStore.context_bytes` joins
this transaction unchanged. Persist the captured snapshot in a later short write
transaction if necessary; staleness is checked at activation and dispatch.
Never label graph as-of views as historical legacy execution snapshots.

Retain separate component and wrapper limits: complete execution at most 1 MiB;
graph uses existing QueryLimits defaults/maxima; canonical context wrapper at
most 2 MiB, including embedded feedback. Encoding should embed the execution
object without additional base64 expansion of the entire component; retain its
exact canonical component bytes/hash. Oversize fails without dropping evidence.
Reusing execution export deliberately retains VS-002's scaling limitation.

### Candidates and task bindings

`CandidateVersionV1` has controller-owned candidate ID, positive version, prior
version, study/charter binding, immutable source kind/key/hash, description,
intended result, candidate kind, target pins, references and constraints.
Kinds are `explore`, `experiment`, `replicate`, `synthesize`; defer/no-action is
a decision abstention rather than an executable candidate.

Candidate identity derives from study and a stable origin key, not description
similarity or task ID. Registering identical origin/version/content replays;
changed content under the same version conflicts. Append a changed version with
an expected prior version; concurrent revisions cannot both become that version.
New identities can appear in any round; there is no fixed global candidate count.

A source supplies no executable binding in its free-form payload. The trusted
ledger may separately bind a candidate version to an existing task by reading:
study/task ID, full normalized TaskSpec hash, and admission provenance. Accept
existing trusted manual registration, or a VS-002 imported task with matching
approval/import receipt. Do not require planner approval for manually admitted
tasks. Unapproved/unimported/absent tasks cannot be bound. Verify proposal-backed
bindings against the immutable approval and receipt; do not require the old
approval context still to be current after import.

Changing a binding requires a new candidate version. Do not adopt a manual task
as an imported proposal. Candidate kind/text never chooses worker kind. Two
candidates mapped to the same task in one decision are invalid. An unmapped
candidate can be valued and ranked but cannot dispatch.

### Estimates and policy

Each considered candidate gets an immutable, versioned impact judgment and cost estimate record stored with its decision
membership: candidate version, context hash, assessment/estimator identity and
exact input/feedback refs, **fallible scientific impact assessment with rationale,
assumptions, uncertainty, alternatives, and qualitative/unknown/incomparable status**,
optional numerical *synthetic* contribution proxy, information-value estimate,
and separately modeled resource cost vector. Only quantitative predictions require
units and values/intervals or an explicit unknown reason. Preserve assumptions and calibration provenance
(`synthetic_uncalibrated` for fixture estimates). Do not force probabilities or numerical research-impact scores; a mathematical heuristic cannot completely establish scientific importance.

Cost dimensions include wall/CPU/GPU seconds, LLM tokens, human minutes and money
with currency if used; unsupported/unknown fields remain distinct from zero.
Fixture resource tokens have an explicit synthetic unit. No vector-to-scalar
exchange is implicit. An estimate is not Evidence or a validated claim.

Both reference policies receive the same saved context, candidate set, estimates
and constraints. They filter missing required inputs/costs and infeasible
candidates with recorded reasons. Initial policies abstain on graph truncation;
an intentionally selected, untruncated view may produce a qualified ranking.
An excluded candidate remains in the ledger with its estimate and reason.

The static baseline sorts by saved origin order after common feasibility filters.
The information policy sorts the **synthetic fixture's** proxy values by `direct_value + weight * info_value` in expressly synthetic units with a nonnegative declared weight. It exists to exercise reproducible policy code, not to compute true scientific importance; preserve the manager's scientific reasoning separately.
Apply resource ceilings per dimension before scoring; do not divide by costs.
When scientific judgments are incomparable or required inputs are missing, retain that qualification; an explicitly versioned policy may request evidence, use a disclosed tie-break or abstain instead of inventing a score.

Policies output integer priority groups, lower first. Total order is priority
group, candidate ID by UTF-8 bytes, version. Persist group, ordinal and factors
actually used, including ties, exclusions, qualifications and abstention reason.
No Store, authorizer, graph writer or executor is passed to these functions.

**The following is a synthetic engineering scenario, never a validated measure of research impact.** For the initial estimator fixture, use a revealed branch state `unknown`,
`viable` or `nonviable`. Each candidate's versioned synthetic metadata contains
two nonnegative integer direct values (one per branch), a diagnostic information
bonus, a branch-relevance flag and an initial cost vector. While the branch is
unknown, direct estimate is the floored arithmetic average of its two values,
with their min/max as an explicitly uncalibrated interval. Once revealed, use
that branch's value. Information estimate is the configured bonus only for a
relevant diagnostic while the branch is unknown; otherwise it is zero. These
are fixture heuristics, not posterior probabilities or a claim of true VOI.

An illustrative required case uses A values 8/8, B values 1/1 and information
bonus 12, and C values 14/0. With weight 1 and all inside the same per-dimension
synthetic resource ceilings, B outranks A initially. After viable feedback C
outranks A; after nonviable feedback C falls below A. D can be introduced from
the revealed state in a later round. A known/redundant branch removes B's bonus.
The static comparator retains origin order A/B/C. Add an adverse case where the
heuristic information bonus is misleading rather than always rewarding B.

For engineering wall-cost prediction, use the median available completed-run
wall_seconds for the same fixed worker in the saved execution snapshot, with
observed min/max as an uncalibrated range; before observations, retain the
configured fixture prior and mark its source. Never update CPU or scientific
impact from a task-success flag. Synthetic resource-cost surprises update only
the explicitly revealed synthetic vector, with that source recorded. Missing
observations remain unknown. All rules and parameter values are saved/versioned.

## 4. Proposed service surface and replay

These signatures describe behavior; record/dataclass names may remain small
implementation choices once approved. `operator` is a trusted local caller
assertion supplied outside research payloads, not authenticated identity.

| Internal operation | Inputs | Result / side effects |
| --- | --- | --- |
| `migrate_decisions(store)` | Explicit known v3 database | Verified v4 or already_current; no implicit earlier migration |
| `capture_context(store, selection, revealed_feedback)` | Versioned bounded query and explicit fixture input | Immutable context ID/hash and manifest; no research-state changes |
| `record_candidates(store, request_id, definitions, bindings, actor)` | Bounded candidate definitions and separate trusted optional bindings | Immutable versions/receipt, atomically; no task creation |
| `decide(store, request_id, context_id, candidates, estimator_config, policy_config, constraints, actor, previous_decision_id=None)` | Exact versions and configurations | Immutable decision plus complete member estimates, ranks or abstain |
| Trusted automatic priority publication (signature TBD) | Manager's saved ranked decision, context/policy/verified bindings and expected predecessor if needed | Controller records active priority without a human activation each round; no execution |
| Internal ranked dispatch helper (signature TBD) | Called only by v4 `run-next` with verified current/reusable manager preference | Independently scans the full ready set and claims at most one task, without policy/model inference in the claim transaction or a duplicate executor |
| `show_context/decision/selection/dispatch`, `list_decisions` | Exact ID or bounded page query | Saved payloads and complete per-decision membership; linked run state explicitly current |

All request IDs bind full normalized inputs and actor/source. Exact committed
replay precedes freshness/current-head checks and returns history without new
rows, selection changes, algorithm calls or execution. Conflicting key reuse
raises `conflict`. Pure decision calculation may happen outside the write
transaction from immutable inputs; decision, members and request/result receipt
commit atomically. A rolled-back deterministic calculation may be retried only
by an explicit call. There is no uncertain provider or automatic background retry.

Require no more than 64 candidates/round or registration batch, 64 refs/candidate,
4 KiB per text field, depth 32 and 256 KiB canonical decision result including
all members. Membership query returns all considered candidates or fails; never
silently truncates alternatives. Inspection pages default to 32 and cap at 64,
with explicit continuation and 2 MiB response cap. Context lookup may use that
cap; an oversized page reduces page length with continuation or fails for a
single oversized item. These proposed version-1 limits need approval with the
contract and can evolve through explicit versions.

## 5. Activation, freshness and dispatch

### Automatic priority determination and publication

**Accepted V4-13:** Research Manager automatically chooses and updates task priorities. A trusted controller validates study/charter, candidate-to-admitted-task bindings, context and policy versions and persists the effective scheduling preference **without a human operator activating each round**. The model cannot authorize tasks, approve/import proposals, choose a new worker, retry tasks or trigger execution.

**Permitted narrow implementation choice:** a trusted controller may publish a validated decision atomically with saving it, or as a separate deterministic controller step without human intervention. Either records provenance, prevents stale-head overwrites and cannot treat model-provided actor fields or research text as capabilities; publish the chosen v1 transaction contract before coding.

**Preferred ADR-027 lifetime:** one published recommendation may guide **multiple committed claims** as long as each claim passes current authority/readiness checks and an independently recorded Replanning Policy assessment. Recommendation publication is not an execution grant. Replaying prior receipts does not schedule or re-execute work.

A recommendation becoming available never starts a worker. Dispatch remains an explicitly invoked trusted scheduling operation.

### Original context identity versus continuing applicability

**ADR-027 preferred direction:** distinguish the immutable context originally used to create a recommendation from a fresh determination that the recommendation remains applicable. A new run, evidence record or graph sequence changes the *current state*, but need not require a complete new research-impact judgment. Keep study/charter, immutable policy and trusted execution profile binding strict; never weaken existing VS-002 context/approval freshness.

Create a versioned **Replanning Policy** contract (precise schema unapproved). It records a bounded evaluation of changes in explicitly consulted premises: relevant evidence/hypothesis revisions, dependent candidate assumptions, resource costs, new candidates and baseline transitions. It may respond with reuse, replan, hard refusal for an unverifiable/critical invalidation, or reasoned defer. Record input versions, evaluator identity, reasons, uncertainty, observed/predicted evaluation cost and whether the original context was partial. A full recomputation is optional when relevant changes are small; there is no claim that scientific impact or the expected value of replanning can be determined exactly.

A changed global graph sequence or execution hash is a *change detector*, not an unconditional ranking-expiration rule. Evaluate relevance safely; an unknown critical premise must not be treated as stable. Existing status/dependency/capacity/permission/worker constraints are authoritative at **every** claim regardless of rank reuse. Do not run expensive manager assessment inside a claim transaction or infer that stale rankings automatically remain valid.

Multi-claim reuse requires multiple immutable dispatch receipts referencing one recommendation and separate validity/replanning records. Do not consume a ranking by its first claim or rewrite it to remove completed tasks. Implement a **bounded deterministic first policy** with explicitly synthetic relevance classifications and conservative refusal on unknown critical premises; document exact read-set, time/cost budget and race semantics in the v4 internal interface before coding. Real scientific relevance prediction and universal replanning value remain future research.

### Dispatch transaction, independent readiness and outcomes

Use the original controller lock and `BEGIN IMMEDIATE`. Replay a committed dispatch receipt before any new work; refuse an unfinished running attempt. **Independently enumerate all admitted, pending, dependency-ready tasks** from the authoritative task and dependency tables, rather than deriving the available-work set from ranked candidate IDs. Check worker profile and capacity separately. A zero ready set causes no execution and must be distinguished from an active run, absent pending work, blocked prerequisites, recommendation failure and actual study completion.

If ready work exists, verify the controller-published ranked decision, exact bindings, **the latest relevant Replanning Policy reuse/recompute decision** and currently binding hard constraints inside the claim transaction. Intersect the rank with the real ready set, skip blocked entries, and audit blocker IDs. If a relevant change requires expensive re-evaluation, perform it outside the transaction and atomically recheck inputs before claiming. An unranked prerequisite remains visible as ready work but is never silently promoted by FIFO.

**Accepted V4-12:** If ready tasks exist but the recommendation is absent, stale, incomplete or has no usable mapped ready member, explicitly request a **bounded** Research Manager re-evaluation or return `decision_unavailable`/`needs_decision` with a reason. Do not report `no_ready_task`, use an infinite retry loop, or silently select FIFO. An intentional manager `abstain` has its own recorded reason and is not a model/estimation failure. The exact orchestration interface (fresh decision before the claim versus a separate re-evaluation round) awaits review; never call a model or policy inside the claim transaction.

When a ranked ready task is selected, ordinary pending→running update, run insertion and immutable **per-claim** dispatch receipt (including reused recommendation ID and relevance assessment) commit **atomically**. One rank may link to several claims. Run only the existing fixed worker, using original execution validation/finalization after commit. A receipt never silently retries work if its response is lost.

| Authoritative state | Proposed durable result | Worker execution |
| --- | --- | --- |
| Running/unfinished attempt occupies capacity | `review_required / unfinished_attempt` or `busy` | None |
| No pending admitted task | `no_ready_task / empty_queue` | None; not scientific completion |
| Pending tasks exist but all prerequisites are unsatisfied | `no_ready_task / prerequisites_blocked`, with blockers | None |
| Ready tasks exist but ranking missing, unranked or critically invalid | `needs_decision / missing`, `critical_invalidity`, `no_ranked_ready_task`, or `decision_failure` | Bounded re-evaluation or none; **never FIFO** |
| Manager explicitly defers despite ready tasks | `deferred / reasoned_abstention` | None |
| At least one admitted ready task has applicable current or **reusable earlier ranking** | `claimed` with task/run/recommendation, relevance check and audit | One existing-worker attempt per invocation; future invocations may reuse the same ranking |

Corrupt or forged bindings, cross-study references, schema/limit/persistence failures must fail atomically, not be treated as harmless blockers. Replayed valid non-claim outcomes return their historical receipt and a new attempt requires a fresh request ID. The public interface names and exact re-evaluation trigger remain **proposed**, not accepted signatures.

### Resource and admission boundary

The trusted execution profile allows only the existing fixed worker, one active
run, existing five-second subprocess timeout/output checks and no worker-selected
network/API/GPU/human action. Its code/configuration hash is pinned. Recheck it
and admission/readiness under the claim transaction, then retain the executor's
own validation. No prediction can enlarge this profile.

Policy resource ceilings are synthetic feasibility checks, not reservations.
Real CPU/memory/cumulative-money/wall-time budget guarantees do not exist in the
current controller. If an action requires such a hard guarantee, reject it as
`unsupported_resource_constraint`; never execute on the strength of a favorable
estimate. Do not claim that a subprocess timeout enforces total controller wall
time or that null CPU cost is zero. Implementing new real resource accounting
would require a separately approved contract.

### Approved v4 `run-next` entry point

On v1–v3 preserve **exact** existing `run-next`, `Store.claim_next`, CLI/error/JSON and FIFO behavior. On explicitly migrated **v4 the same `python -m arf run-next --db PATH` command** must compute or reuse a controller-validated Research Manager ordering, independently verify all ready tasks and claim **at most one** eligible admitted task with a transaction-owned ranked-claim helper. Direct `Store.claim_next` FIFO selection on v4 must refuse; a new public dispatch verb is not needed.

Recommendation computation/publication **never by itself executes a worker**. The v4 CLI may add ranked recommendation/dispatch IDs and distinguish `no_ready_task` (truly no ready work), `needs_decision` (ready work but no usable ranking) and `deferred` (reasoned abstention). Exact v4 response/error shapes and helper signatures must be specified in additive `docs/interfaces-vs004.md` **before code changes**. The schema-versioned behavior change is explicitly approved in ADR-028.


## 6. Persistence and compatibility

Use a minimal immutable ledger, building on the technical review's six tables:
contexts, candidate versions, decisions, decision members (impact judgments and
estimates), controller priority-publication events and dispatch receipts.
**Include versioned reuse/replanning assessments**, as an additional immutable table or equivalent constrained append-only linked records in the approved v4 schema. Canonical versioned payloads retain
configs, reasons, exact input IDs and hashes. Add only indexes/receipt support
needed for these operations; no general event engine or independent reward store.
Candidate registration batches additionally need a small request-receipt table
binding request ID, full request/actor hash and returned versions; it commits
with the batch, including when all versions already exist. This avoids losing
the binding for a new request ID that only refers to existing candidate rows.
Other operation receipts live in their corresponding substantive tables.

Enforce same-study references, exact candidate-version membership, selection
predecessor checks, unique request IDs, unique member ordinal and candidate per
decision, nullable ranks only for excluded members, and unique claimed run.
**Do not enforce uniqueness of claimed activation/recommendation:** one valid
ranking can guide several distinct claim receipts, each with its own trusted
replanning/applicability record. Bind task/run via composite foreign keys; verify typed graph
refs and spec/admission hashes in the trusted service. Add update/delete guards.
Never duplicate scientific observations into the decision ledger as new Evidence.

Migration must verify known v3 schema and foreign keys, add v4 objects and set
user_version in one rollback-safe transaction, then verify exact known v4.
Repeat on verified v4 is read-only already_current. Unknown/customized schemas
are refused unchanged. Preserve all legacy rows/bytes/hashes/IDs, sequences,
triggers, statuses, nulls and receipts. No task/observation backfill or relabeling.

Update known-version handling in Store, PlanStore, GraphService, plan migration,
graph migration and full schema verification. `init` stays v1. On v4, old plan
and graph migrations verify compatibility and return their existing compatibility
version 2/3 already_current responses without downgrade. All new ledger writes
are excluded from legacy export-v1. Old binaries may refuse v4; no downgrade.

## 7. Required offline scenario

After approval, add a deterministic harness requiring a fresh path and separate
process restart inspection. Use only the demo charter fixture and existing
authorized fixed-worker task setup; no recorded study charter is edited.

Start with at least three candidates: immediate-value A, informative diagnostic
B, and uncertain follow-up C. Candidate D arrives only after feedback. Include
an attractive unmapped/non-worker action and a mapped high-ranked blocked task.
Run static and information-aware policies on identical captured inputs; save
both decisions. The trusted controller must **automatically publish** the chosen
manager priority without a fixture operator's per-decision activation, then
explicitly dispatch actual demo workers in the ranked order across new rounds.

The estimator must calculate contribution/information/cost updates from revealed
feedback rather than pick a winner by round number. Have one actual experiment
outcome reveal a fictional branch through a pinned fixture rule; the alternative
permitted feedback must change a later recommendation. Keep a private oracle
outside candidate/context/estimator/policy inputs until feedback is revealed.
Persist revealed synthetic state only in its clearly labeled context payload.

Include a misprediction, cost surprise, inconclusive/contradictory unreviewed
assessment, explicit operator baseline change and candidate arrival. Demonstrate
**at least two claims from one recommendation** when execution-state changes are
unrelated to its scientific assumptions, and a later *relevant* observation that
triggers a traceable replan. Record the time/cost of checking applicability
separately from computing a new ranking; never assume assessment is free. Measured
wall-time updates are engineering cost observations; synthetic utility stays
separate from actual runs/evidence. Show a case where information seeking loses
to the static policy or pursues irrelevant/redundant information. Do not promise
one policy always wins. A truncated context abstains and claims nothing.

## 9. Approved implementation process and stop conditions

The owner approved the bounded D1–D13 offline scope and v4 `run-next` behavior as ADR-024–029. This is **implementation authorization**, not a claim of completed implementation or scientific success.

1. Re-read `AGENTS.md` and current code, record baseline tests and preserve unrelated changes.
2. **Before implementation**, author `docs/interfaces-vs004.md` defining internal contracts, versioned canonical payloads, the exact v4 `run-next` output and error/no-action semantics, admission-binding validation, bounded relevance policy, concurrency/transaction boundaries and additive SQLite v4 DDL. This document must keep v1–v3 external contracts exactly unchanged.
3. Implement a deterministic, conservative **Replanning Policy v1**. It must be able to *reuse* a recommendation after a proven noncritical change under an explicitly attributed **synthetic scenario scope**, *recompute* after known relevant changes, and *refuse/defer* after unknown critical changes. A global graph/execution hash difference is a change detector, **not** an automatic expiry rule. Do not classify scientific evidence as irrelevant merely because it lacks a graph link. Any claimed relevance judgment must be inspectable and context-bound. Do not pretend mathematical impact is complete or calibrated.
