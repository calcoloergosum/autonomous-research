# VS-001 — Persistent research-task execution vertical slice

**Status:** Ready for Codex implementation.  
**Type:** Local reversible implementation; no external actions.  
**Priority:** First milestone.

## Goal

From a human-defined demo study charter, create a research task in SQLite, execute one allowlisted local numerical experiment, record observed result + actual wall time + linked evidence, and resume inspection after a process restart. Failure and interrupted runs must not be misreported or silently retried.

## Must implement

1. Python 3.11+ package importable as `arf` and CLI at `python -m arf`.
2. Charter YAML validation + persisted immutable snapshot/hash. Required fields and error behavior per `docs/interfaces.md`.
3. SQLite schema/migration (single DB), task creation/list/show with same-study dependencies and cycle validation.
4. Atomic ready-task claim; for VS-001, stable FIFO ready selection, one task executed per `run-next` invocation.
5. One bounded, allowlisted local `demo_mean` worker with validated input/output and deterministic result. Never accept command text or arbitrary code from task data.
6. Run history including start/end timestamps, status, error/exit information, observed wall time, observed demo cost fields; successful result creates **unvalidated** evidence linked to the run.
7. Recovery from interrupted `running` state with no automatic re-execution; explicit `task retry` for demo tasks only; history preserved.
8. Tests for acceptance and failure paths. Update README with *actual* setup commands and `docs/current-state.md` with observed status.

## Contract and example

Use the exact normative semantics in `docs/interfaces.md`, `examples/demo-charter.yaml` and `examples/demo-task.json`.

Required CLI shape:

```bash
python -m arf init --db .local/arf.db --charter examples/demo-charter.yaml
python -m arf task add --db .local/arf.db --spec examples/demo-task.json
python -m arf task list --db .local/arf.db
python -m arf run-next --db .local/arf.db
python -m arf task show --db .local/arf.db --id demo-mean
python -m arf evidence list --db .local/arf.db
python -m arf recover --db .local/arf.db
```

Expected numerical worker outcome: mean `5.0`, count `4`. Actual duration must be **measured**, never a hardcoded estimate.

## Acceptance scenarios (automated tests)

- **A1 Normal:** import valid charter; create demo task; execute; task is succeeded; exactly one succeeded run and one unvalidated evidence row with value `5.0`; wall_seconds nonnegative.
- **A2 Restart:** exit CLI, start a new process and query same DB; study, task, run, evidence, and costs persist unchanged.
- **A3 Dependencies:** task B depends on A; B cannot start before A succeeds. A missing/cyclic dependency is rejected at creation. `run-next` selects ready tasks deterministically.
- **A4 Immutability:** reimport identical study charter does not rewrite; changed question/criteria or same ID with changed source is rejected. There is no agent-write API for modifying stored question.
- **A5 Failure:** malformed task input is rejected before execution; separately, simulate a worker exception, timeout, or invalid worker output through a test-controlled executor seam. An accepted task whose execution fails becomes failed with a failed run/error record and no successful evidence. Do not enable user-supplied code merely to create a failure test.
- **A6 Crash recovery:** simulate a persisted active run (a process crash may be simulated at the persistence boundary); `recover` moves it to interrupted/needs_review; second `recover` changes nothing; no auto rerun. Explicit retry creates a **new** attempt without overwriting history.
- **A7 Claim safety:** repeated or concurrent `run-next` must not result in two successful claims/runs of the same task. Use SQLite transactional concurrency control and test interleaving where feasible.
- **A8 Idempotent observation:** querying or retrying recovery does not duplicate evidence or create fake results.
- **A9 Security boundary:** task spec with arbitrary shell command, unsupported kind, external URL or raw Python code is rejected rather than executed.

## Non-goals — do not implement

- No actual autonomous Research Manager, impact/cost predictors, exploration/exploitation algorithms, baseline revision, vector store, dashboard, Codex SDK integration, cloud API calls, or GPU scheduling.
- No production-purpose arbitrary shell command execution or generated-code evaluation.
- No automated human task queue or approval orchestration.
- No fully distributed recovery, exactly-once execution guarantee, or multi-host cluster features.

## Deliverables

- Minimal source tree + packaging (`pyproject.toml` or documented equivalent).
- Automated tests and working demo CLI with local DB.
- Documentation updates: actual commands/results in README and `docs/current-state.md`.
- Final Codex report: changed files, design assumptions, tests executed/results, limitations, outstanding approval questions.

## Stop condition

If a required choice materially changes the public command/JSON contract, schema interpretation, security boundary, ownership of the final question, or intended restart semantics, do not guess; present the decision with options. Otherwise use a simple reversible local implementation and proceed.
