# VS-003 — Minimal Research Graph implementation specification

**Status:** Approved by the human owner and implemented/verified offline (2026-11-10), limited to G1–G10. See `docs/current-state.md` for actual results and limitations.
**Source:** [VS-003 design proposal](VS-003-proposal.md), reviewed 2026-11-10.  
**Target:** An offline, persistent research provenance graph, compatible with completed VS-001 and VS-002.  
**Authority:** This is the approved narrowed implementation contract for VS-003, reflecting ADR-016–023 in `docs/decisions.md`. It authorizes local offline implementation and regression testing within this file; it does not authorize substantive research, external API/model calls, spending, arbitrary generated-code execution, charter changes, or VS-004/VS-005 work.

## 1. Scope and success definition

Implement the smallest trustworthy Research Graph capable of answering:

1. Why was a subordinate inquiry or task proposed or registered? Distinguish a recorded motivation from scientific causation and a retrospective attribution from contemporaneous proposal provenance.
2. Which exact task attempt created a particular observation, and how was that observation interpreted in relation to a specific hypothesis revision?
3. Which further investigations were motivated by that result, possibly along multiple branches or from several sources?
4. What did the recorded graph say at an earlier graph revision, even when an interpretation is later revised or withdrawn?
5. When an operator records a new baseline, which previous baseline and research directions were affected, without altering existing execution tasks?

A successful vertical slice demonstrates a branching investigation, convergent/competing evidence, a revised interpretation, and a scoped baseline transition using *offline fixture data* and previously existing safe demo executions. The graph does **not** assess scientific truth, approve executable work, choose a research policy, or produce a final answer.

### Explicit constraints

- The final study question/criteria/constraints remain human-owned, immutable and sourced *only* from the existing study charter.
- The VS-001 execution DAG and the VS-002 proposal/approval/import pipeline keep their existing semantics. Graph edges must not create ready work, change dependencies, authorize tasks, retry runs or reclassify evidence.
- This is a single-host, single-study-per-database, Python/SQLite extension; no live models, network, external spending, arbitrary generated code, or new worker types.
- Graph read/write is bounded and local; no UI, progress monitor or graph viewer (reserved for VS-005).
- D1–D8 are approved as ADR-016–023. The historical proposal's broader options are not authorization for additional implementation.

## 2. Recommended architecture

**Approved D1 (ADR-016):** Maintain the execution DAG as the authoritative `dependencies` table. Add *separate typed semantic relationships* in the same SQLite database, sharing IDs of existing studies/tasks/runs/evidence. A combined graph read projection may expose execution and semantic edges with different categories, but **only** existing `dependencies` changes scheduling eligibility. Graph services cannot mutate that table.

**Approved D2 (ADR-017):** Explicit transactionally verified **schema v3** migration, additive to the v2 database. Store immutable ideas, revisions, baseline snapshots, attributed semantic relationships and small append-only correction/transition records. Avoid a new graph DB and avoid building a generic event-sourcing runtime.

### Minimal node roles

| Role | Authority, identity and VS-003 handling |
| --- | --- |
| O — ultimate question | Typed reference to the existing `studies` row; read-only charter body and exact source hash. Exactly one O per study. No writable objective node. |
| Q/H/C — subordinate question, hypothesis or claim | Graph-owned stable `idea_id` with immutable `kind` and append-only `idea_revision_id` text/assumptions/scope. Claims are interpretations, never observations. |
| T — research task | Read-only reference to existing study/task ID and immutable TaskSpec; never graph-owned executable task. |
| R — attempt | Read-only reference to existing run ID, including failures/retries. |
| E — evidence | Read-only reference to existing evidence ID and its original unvalidated label. |
| B — baseline | New immutable graph-owned baseline ID, scoped method/configuration and pinned references. It never overrides charter criteria or alters executable task specs. |

Use stable opaque IDs for new ideas/edges/baselines; pin exact revisions for interpretive claims. Legacy IDs retain their meaning. Avoid copying authoritative task/run/evidence content into a parallel mutable node body. Proposals, contexts and import receipts remain provenance sources, not scientific evidence.

### Minimal semantic edge vocabulary

All graph semantic edges must have a named type, typed directed endpoints, study binding, provenance, exact revision pins where applicable, author/source attribution, recorded timestamp, and unreviewed/withdrawn visibility.

| Type | From → to | Exact meaning |
| --- | --- | --- |
| `ADDRESSES` | Q/H/C → O/Q | Declared intended research relevance; not proof that the objective is addressed. |
| `INVESTIGATES` | T → Q/H/C | Declared experimental intention, not execution or design adequacy. |
| `MOTIVATED_BY` | Q/H/C/T/B → Q/H/C/E/B | Attributed reason for proposing/adopting the source. Not a scientific `CAUSES` assertion. |
| `DERIVED_FROM` | Q/H/C → Q/H/C/E | Claimed lineage of the *idea content*, not independent evidential support. |
| `ASSESSES` | E/C → H/C | Scoped interpretation with exactly one polarity: `supports`, `contradicts`, or `inconclusive`. Pin target idea revision, assumptions/applicability and rationale. |
| `USES_BASELINE` | T → B | Declared design/comparison baseline, not a verified statement about executed configuration. |

Additional read-only factual edges are derived from existing rows, never inserted by a planner: `DEPENDS_ON` T→T from dependencies, `ATTEMPT_OF` R→T from runs, and `PRODUCES` R→E from successful run/evidence linkage. Failed/interrupted runs never produce a successful evidence link. Do not silently treat proposal `evidence_refs` as `ASSESSES` or `MOTIVATED_BY` links.

For baseline replacement, derive `SUPERSEDES` Bnew→Bold **only** from a recorded operator-authorized scoped transition. Do not add an arbitrary writable `SUPERSEDES` semantic edge in this slice; idea-to-idea replacement can be deferred.

No generic `CAUSES` relationship, transitive scientific entailment, claim truth inference, or graph-centrality-derived evidence validation.

## 3. Registration, provenance and mutation contract

### Research note registration

- Register a *valid, persisted* VS-002 `research_note` proposal explicitly, yielding exactly one initial Q/H identity and revision plus an immutable registration receipt, uniquely bound to `(study_id, proposal_id)`.
- This is **not** VS-002 task authorization/import. It creates no Task, Run, Evidence, approval or claim of scientific validity.
- Store exact source proposal ID/hash, captured context hash, author attribution, content and registration time. Unregistered notes remain intact and inspectable in VS-002.
- Same request/operation replay returns the existing receipt; conflicting reuse fails. `no_action`, invalid/uncertain requests and `task_candidate` cannot be registered as Q/H.
- Allow a local trusted human-authored subordinate Q/H as a separate explicitly attributed path; do not invent fake planner provenance.

### Semantic links and changes

- Allow adding a valid semantic edge only through a trusted graph service that validates type, source/target, study, exact revision pins and caller capability. New edges are **unreviewed assertions** by default.
- Every relationship records whether the motivation was **present in recorded creation-time proposal context** or is a **retrospective attribution**. Do not label a link as contemporaneous just because it was registered near task creation; verify the original proposal/request provenance. For graph registrations created after legacy work, default to retrospective/unknown as appropriate.
- Support append-only idea revision and semantic-edge revision/withdrawal with an expected-head check. Previous revisions and withdrawn assertions remain queryable. Changing an assessed target revision does not inherit old assessment or any previous review.
- No general human scientific-review workflow is required yet. If a trusted operator corrects an assertion, record an attributed replacement/retraction rather than deleting or silently upgrading it. A scientific `validated` flag is **not** a graph write.
- Mixed semantic cycles are allowed with visited-set bounded traversal. Execution `DEPENDS_ON` remains a DAG; any `DERIVED_FROM` revisions must not create circular derivation lineage. Avoid a mandatory whole-graph acyclicity check.

### Premises and evidence

- Assessments remain source- and scope-specific. One E may support H1 and contradict H2 under different assumptions; an absent assessment means unknown, not negative evidence.
- For a *joint* synthesis, represent an explicit C revision with a bounded list of pinned premises and `joint` marker, plus lineage links; never count C and its original E premises as independent experiments.
- Keep only minimal premise metadata necessary to distinguish joint from independent contributions. General argumentation logic, automatic contradiction propagation, likelihood inference, independent-evidence proof and scientific review/certification are deferred.
- Original E remains `unvalidated`. A claimed reviewed interpretation, if ever supported later, is distinct from validation of the original observation and from meeting charter success criteria.

## 4. Baseline recording (bounded feature)

**Approved D6 (ADR-021):** Support immutable scoped baseline snapshots and an *explicit trusted-operator* transition from old B to new B, recording rationale, motivating exact E/C references, expected prior active baseline, and a small list of affected task/idea IDs with dispositions such as `retain`, `redirect_proposed`, `pause_direction`.

- The active baseline is a read projection of committed transitions **by scope**, not a global mutable pointer.
- Concurrent transitions from the same predecessor cannot both commit; repeated identical transition operation returns its receipt.
- A transition never cancels pending/running work, changes its TaskSpec, schedules newly proposed work, edits prior results, or alters the final question. Reversion is another append-only transition.
- Avoid implementing an autonomous baseline-selection algorithm or an exhaustive impact recalculation. If transition semantics prove to require major new task lifecycle APIs, stop and present a narrower option for approval.

## 5. Persistence, legacy compatibility and historical semantics

### Schema migration

- Add a **manual** `v2→v3` migration with known-schema verification, SQLite foreign keys, indexes, immutability guards and transactional rollback. An unmigrated v1 DB first uses the existing explicit `v1→v2` path.
- Existing code must continue operating on v1/v2 without implicit migration. On v3, all VS-001 and VS-002 commands continue with **identical** externally visible behavior.
- Preserve all old charter source bytes/hash, task IDs/specs/dependencies, run/evidence rows, cost observations (null vs zero), proposal/request/context bytes/hashes, decisions and receipts *exactly*. Test populated v2→v3 migrations and restart.
- Do **not** add graph fields to the existing VS-002 export-v1 canonical snapshot or hashes. A graph-only mutation must not stale a legacy VS-002 task proposal; execution-state mutations continue to do so.
- Do not attach new graph context semantics to an old proposal/authorization and silently claim it was graph-aware.

### Audit and time

- Give committed graph mutations a monotonic per-study **graph sequence**, append-only operation receipt, controller-observed commit time and actor/source; replays return the same result without advancing the sequence.
- Graph-as-of(S) reconstructs the **recorded graph assertions/revisions** through sequence S, including withdrawn/replaced history. It does *not* reconstruct all legacy execution status at that instant: existing task statuses are mutable and the legacy executor is not fully event-sourced.
- When a view mixes graph history with the current task state, label that state `current`, not historical. If historical execution cannot be established from persisted records, report it as unknown; do not infer backdated motivations.
- Use a consistent transactional write for one logical graph mutation, its revisions and receipt. No LLM/provider/worker calls inside DB transactions.

## 6. Minimal internal operations and offline use

**Approved D8 (ADR-023):** Implement a typed internal graph service plus a deterministic offline fixture harness/tests. Do **not** add new public CLI verbs until a separate contract review. The internal service should support:

1. `register_note` and `create_human_idea` (Q/H), plus a graph-owned C for an unvalidated synthesis.
2. `revise_idea`, `add_semantic_link`, `revise_or_withdraw_link`, with expected-head and operation-id idempotency.
3. `create_baseline` and `record_baseline_transition` with exact source/reason references and operator checks.
4. `read_graph` and bounded `ancestry(task_id)`, `affected_by(evidence_id)`, `as_of(graph_seq)` query helpers.
5. Derived factual projection of existing task dependencies, run attempts and evidence sources, with immutable original IDs and provenance.

Do not prematurely freeze public Python API signatures. Before coding, write an additive `docs/interfaces-vs003.md` specifying actual internal request/result contracts, validation failures and chosen minimal schema. The harness can call trusted service functions; it must not create an executable task through a graph operation.

Every traversal has explicit depth/node/edge/output limits and a visible `truncated` flag / frontier. Node/edge lookup supports stable IDs and typed filters. No mandatory whole-graph snapshot, all-pairs reachability, or graph renderer.

## 7. Offline worked scenario

Build a deterministic fixture, clearly labeled *synthetic*, that exercises all three paths:

- **Branching:** Create H1, link T1/T2 to H1, use actual allowed `demo_mean` attempts to generate E1/E2. Record a scoped supporting assessment and a scoped contradictory/inconclusive assessment as separate unreviewed links. Create Q2 and T3's attributed research intent from E2; keep any task creation/approval in existing VS-002 pathways.
- **Converging:** Let E1/E2 bear on the same H revision, also assess a competing H2 under explicit assumptions. Record a C with a *joint* E1/E2 premise set and do not treat C as a third independent experiment.
- **Baseline:** Create B0 and B1, link a task to B0 as declared comparison context, and record a scoped, explicitly operator-authorized B0→B1 transition motivated by existing evidence/claim. The previous run, pending tasks and charter remain intact.
- **History:** Revise an assessment and withdraw a motivation, then query an earlier graph sequence to recover the prior assertions. Label any task status shown as current/unknown, never as a reconstructed historical fact.

All graph-only fixtures must preserve the existing demo worker allowlist. If necessary, prepare multiple approved demo tasks with different IDs and inputs using existing human-controlled VS-001 commands; do not add fictitious successful evidence rows.

## 8. Required acceptance criteria

| Test | Required observation |
| --- | --- |
| **G1 Objective** | O always resolves to the imported charter; graph requests cannot edit or supersede its question, criteria, source bytes/hash or permissions. |
| **G2 Migration** | Populated v2→v3 preserves every existing row and canonical context exactly; repeat is no-op, interruption rolls back, unknown versions fail, and old v1/v2 operations remain available. |
| **G3 Note registration** | Explicit note registration creates one unresolved Q/H and one replay-safe receipt, no task/evidence; invalid/no_action/task proposals are rejected. |
| **G4 Typed links** | Enforce endpoint types, same-study references, exact revision pins, no dangling premises, no forged factual links, no self-link; multi-source and mixed semantic cycles are representable without changing the execution DAG. |
| **G5 Evidence** | R→E projection requires actual successful evidence; E1 can support H1 and contradict H2 without changing any `unvalidated` field or inferring scientific truth. |
| **G6 Changes** | Revising an idea/assessment or withdrawing a motivation appends new state; earlier revisions and attribution remain queryable; stale expected-head writes conflict. |
| **G7 Time** | As-of sequence reproduces recorded graph state; late links are absent from earlier views and historical execution-status claims are not fabricated. |
| **G8 Baseline** | Scoped B0→B1 transition preserves history, refuses concurrent stale predecessor and replays idempotently; no task cancellation, mutation or auto-start. |
| **G9 Compatibility** | Full existing VS-001/VS-002 regression suite passes on appropriate schema versions including v3; graph-only writes do not alter VS-002 legacy context/export/freshness or execution results. |
| **G10 Safety and bounded queries** | Invalid graph text/roles/approval claims do not create execution rights; bounded graph reads report truncation; fixture runs offline without generated code or network. |

A **small deterministic synthetic scale fixture** (for example hundreds to roughly a thousand nodes) may test bounded traversal and indexes, but a 10,000-node benchmark and hard performance target are intentionally deferred. Report observed query timings only if measured.

## 9. Out of scope

- Automated research planning, graph-bound LLM context/proposal/approval v2, exploration–exploitation allocation, impact/cost predictors and budget scheduler.
- Full scientific reviewer workflow, evidence certification, final-study completion, statistical inference, automatic support propagation, theorem proving and causal discovery.
- Generated-code execution, new experiment workers, real datasets, human data-collection queue, API/network access and external expenses.
- Portfolio-wide automated baseline selection, automatic task retirement/cancellation/retry, or implicit mutations of running/pending work.
- Interactive graph rendering, dashboard, monitoring event stream and VS-005 UI.
- Dedicated graph database, general event bus, distributed operation and cross-host exactly-once guarantees.

## 10. Approved decisions and explicit deferrals

The following selections are **approved** for this bounded implementation and recorded as ADR-016–023 in `docs/decisions.md`. They do not adopt broader, unimplemented features from the historical VS-003 proposal.

| Decision | Accepted for VS-003 | Deferred / alternative |
| --- | --- | --- |
| D1 graph separation | Separate execution DAG and typed semantic graph; shared authoritative IDs | Single graph with strict scheduling projection |
| D2 persistence | SQLite schema v3, append-only graph revisions/operation receipts | Dedicated graph DB, full event sourcing |
| D3 ideas and edges | Q/H/C ideas, exact revision pins, limited premise metadata, closed initial edge vocabulary | Reified full argument/hypergraph model |
| D4 research notes | Explicit idempotent note registration; no automatic graph node creation | Automatic projection/registration |
| D5 scientific review | Preserve unreviewed interpretations and attributed corrections; **defer formal reviewer/validation workflow** | Full review and observation review records now |
| D6 baseline | Immutable scoped snapshots and **operator-recorded** transitions; never affect queue | Candidate baseline records only; defer activation |
| D7 contexts | Freeze VS-002 v1 exactly; **defer graph-aware executable planning and new graph context artifacts**; reads use graph sequences/revision pins | New graph-bound proposal contract now |
| D8 interface | Internal typed service plus offline fixture harness; no new public CLI | New reviewed operator CLI |

**The explicit debt:** VS-003 cannot use an LLM proposal to make a graph-aware authorized execution decision; graph contexts and capability delegation remain future work. **Cleanup trigger:** when the first autonomous Research Manager must create/authorize tasks based on specific graph evidence/baselines. Do not silently attach graph state to VS-002 v1. Fine-grained context freshness should be revisited at that trigger to avoid global hash conflicts.

## 11. Implementation process

1. Re-read the repository, verify the current schema/test baselines and preserve unrelated changes.
2. Publish `docs/interfaces-vs003.md` (additive internal contracts, graph v3 DDL, reference validation, context compatibility).
3. Implement graph storage, registration, limited semantic edges, revision/history, baseline transitions, bounded queries, and offline fixtures.
4. Run existing tests plus G1–G10, demonstrate restart and migration with actual preserved v2 data, `git diff --check`, and document exact observations and limitations in `docs/current-state.md`.
5. If a meaningful decision about objective ownership, existing public contracts, security permissions, migration safety or execution semantics becomes necessary beyond this task, **stop for human review rather than guessing**.

**Completion means the graph records *who proposed what, on which evidence, and what changed afterward* with trustworthy linkage. It does not mean the AI can conduct or certify autonomous research yet.**
