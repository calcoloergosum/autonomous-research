# VS-005 — Research Observatory: one decision-audit journey

**Status: IMPLEMENTED AND VERIFIED OFFLINE (2026-11-11).** See `docs/current-state.md` for actual checks and limitations.
**Approved scope:** a bounded, local, read-only observer UI and supporting read model for the *existing* offline research system. This approval does not authorize substantive research, external models/API requests, spending, arbitrary execution, task admission, decision/policy changes or auto-starting workers.
**Human choices:** local browser application; observation-only; automatic refresh; React + Vite + strict TypeScript; first vertical slice centered on *why one existing task was chosen and how that judgment changed*.
**Baseline:** verified v4 `main` as of `b55875baadf9e30e13392e7e9335bc4827112f2a`; check current HEAD before implementation. The broader [proposal](VS-005-proposal.md) is rationale, **not** additional acceptance requirements.
**Normative API/temporal contract:** [`docs/interfaces-vs005.md`](../docs/interfaces-vs005.md); accepted decision [ADR-031](../docs/decisions.md).

## 1. User outcome and deliberately narrow scope

One coherent **Research Explorer** must let an operator:

1. Open an existing v4 DB and identify the study, current task readiness/status and recent actual dispatches.
2. Select an executed or non-executing Task/Dispatch. Trace its *recorded* candidate binding, saved recommendation membership/rank or exclusion, policy/assumptions/context, and final Run/Evidence when present.
3. Understand **why** the recommendation was made **and what alternatives were considered or excluded**. The Research Manager's fixture numbers must be labeled *synthetic proxy*, not objective scientific value.
4. Pin that decision's saved immutable Context, then compare with another decision (the existing B/A/C/D fixture provides an initial vs later ranking).
5. Continue inspecting the selection while a separate trusted process updates the DB; live activity refreshes without page reload. A pinned checkpoint never silently moves.

The first product is **a decision audit**, not a comprehensive research-dashboard suite.

**Required initial screen:** recent work/dispatch list + compact **Why? trace** + persistent Inspector and two-decision comparison. Small explicitly typed source links or a mini-DAG are enough; **no full interactive network graph, three complete pages, general search or universal time slider**. Selected Task/Dispatch and Inspector state persist through refresh and checkpoint comparison; support explicit return to Live.

## 2. Implementation boundaries

- **Backend:** a standalone Python 3.11+ loopback observer process. Start with a small standard-library HTTP server; no new production Python web dependency without measured need and human review. Proposed command `python -m arf.observer --db PATH` (now accepted as the VS-005 observer entry point). **Never** run as a side effect of `run-next` or import.
- **Frontend:** **React + Vite + strict TypeScript**, components for recent list, trace, Inspector and checkpoint comparison. Use a minimal React component-state model; add no router, global state library, graph engine, UI kit or analytics by default.
- **Build/runtime:** pin exact frontend dependencies/lockfile; `npm ci`, `npm run typecheck`, `npm run build` are the reproducible development/build path. The Python server serves locally bundled prebuilt assets; **Node is not required to run the observer**. No CDN, runtime dependency installation or external network access. A clean offline Python runtime must be able to serve the checked-in/release-built frontend assets; decide specific artifact packaging in implementation and document it.
- **DB:** v4 **only** initially; explicit `unsupported_schema` response for v1–v3, corrupt or absent DB. **No migration, table, index, trigger, UI annotations or persisted view state.** Observer must not construct a writer-capable `Store` or invoke write-capable services.
- **SQLite:** use a dedicated URI `mode=ro` connection and `PRAGMA query_only=ON`; short read transactions for coherent cross-table snapshots, bounded scans and output sizes. Do not set `immutable=1` on a live DB. A running writer may require SQLite WAL sidecars; distinguish no DB-content writes from all filesystem effects. A rejected write attempt must never reach an ARF mutation method.
- **Web security:** bind explicitly to `127.0.0.1` only; restrict Host to trusted loopback values and reject cross-origin requests (DNS-rebinding defense). No permissive CORS; restrictive CSP; untrusted research text always rendered as **text**, not HTML/JS; no arbitrary file reads, SQL inputs, external URLs or remote scripts. Only GET/HEAD for static assets and GET for API; other methods fail safely. Avoid revealing the absolute DB path in JSON/HTML.
- **Authority:** observing never creates tasks, candidates, approvals, imports, rankings, graph operations, baseline transitions, dispatch claims, runs, retries or Evidence. No automatic recovery, execution or science validation. Original v1–v4 behavior and admission/authorization boundaries unchanged.

## 3. Exact scoped read capabilities

Use [`docs/interfaces-vs005.md`](../docs/interfaces-vs005.md) for the **versioned response shapes, limits, status/error meanings, snapshot, polling and checkpoint rules**. The initial five GET resources are intentionally sufficient:

- `GET /api/v1/meta`: study identity and schema/observer capability.
- `GET /api/v1/overview`: bounded current work and recent dispatch/decision summaries.
- `GET /api/v1/trace?kind=task|dispatch|run|evidence|decision&id=...`: source-linked task/decision/dispatch/actual run/evidence story, bounded related graph assertions when they exist.
- `GET /api/v1/checkpoint?id=DECISION_ID`: immutable saved Decision Context and the exact decision/members. Fetch twice to compare client-side; **no separate compare API** initially.
- `GET /api/v1/changes?since=TOKEN`: process-scoped generation/epoch for efficient live refresh. **No generic graph, search, execution, timeline or mutation endpoint** in this milestone.

Do not hide important missing or excluded alternatives; paginate or return an explicit incomplete marker. Never return truncated data as complete, and never infer a graph motivation or scientific causality not recorded by the database.

**Read model:** plain read-only SQL/projections over current v4 tables and existing graph query semantics, keyed by exact `study_id`, `task_id`, `candidate_id+version`, `decision_id`, `publication_id`, `assessment_id`, `dispatch_id`, `run_id`, `evidence_id`. Prefer small pure mapper functions and parameterized SQL. A Graph `MOTIVATED_BY` or `ASSESSES` link is an attributed semantic assertion, distinct from factual `ATTEMPT_OF` / `PRODUCES` and the actual dispatch receipt; absent links are labeled `not_recorded`.

## 4. Checkpoints and temporal model

**Top-level UI modes are exactly:**
- **Live:** an atomic read snapshot of current mutable Task status/blockers plus existing immutable history and newest publications. The user can remain focused on an older selected object; `Live` is not equivalent to auto-select-latest.
- **Pinned Decision:** the stored v4 decision and original immutable `decision_contexts` body; a later or earlier decision may be selected as a **comparison target**. New commits cannot silently replace either decision or the old saved context. A `current_execution` section, if shown, is separately labeled and never inserted into the checkpoint context.

A Graph `at_seq` query gives **graph revisions at sequence N**, *not* a third global historical mode. Its T/R/E bodies are currently read execution bodies and existing graph reads label historical execution status **unknown**. Do not pretend graph-as-of reconstructs old Task status.

The comparison between two decisions distinguishes:
- same candidate ID but different version / changed estimate / changed policy / changed rank / exclusion;
- candidate arrived, disappeared from compared membership, or is unmapped;
- changed recorded feedback / graph sequence / execution snapshot;
- different **selection scope** or truncation (cannot attribute every difference to changed research facts);
- unknown/incomparable scientific judgments and missing historical status.

Avoid a synthetic “research complete” percentage and avoid causal language without an explicit recorded attribution. Every projected UI field that could be historical or scientific has a source identity and an appropriate `temporal_scope` or uncertainty/validation label.

## 5. Automatic live refresh

Use **approximately 3-second same-origin HTTP polling** as a reversible default. Server maintains a persistent read-only SQLite change-detector connection and compares **`PRAGMA data_version` on that same connection** between polls. Maintain a process-local random **epoch** plus increasing **generation**; never treat SQLite data_version as a global revision or share it across connections. Detect changes to **any** v4 table, including tasks, runs/evidence and decisions, not graph sequence alone.

On change, client refreshes only active overview/trace content. Preserve selected object, expanded trace, Inspector scroll, comparison selections and pinned checkpoint. Prevent out-of-order network responses from overwriting newer state; server restarts, DB replacement, invalid token, busy DB and disconnect trigger explicit resync/stale signals. Historical pinned content remains immutable through polling. Hidden tabs may pause/slow polling and check once on return. Browser polling must **not** start research actions.

This is a small local single-client baseline; multi-client consistency beyond read-snapshot semantics is out of scope.

| VS5-03 | Select Task B/its dispatch and follow exact candidate binding, ranked decision, **considered and excluded alternatives**, publication/assessment and Run/Evidence links. |
| VS5-04 | Evidence explicitly shows `unvalidated`; predicted costs, observed run costs and synthetic ranking proxies never appear as interchangeable values. |
| VS5-05 | Exact persisted Q/H/C/graph semantic relations retain source provenance and unreviewed semantics; missing motivation is `not_recorded` and is not invented. |
| VS5-06 | Pin an original Decision Context; refresh leaves saved context unchanged, and currently displayed mutable Task status is explicitly `current_execution`. |
| VS5-07 | Compare the original decision with a later D-containing decision; show changed membership/rank, assumptions/feedback and whether different selection scope prevents strong comparison. |
| VS5-08 | Trusted **separate writer** changes graph, task/run/evidence and decision ledger in an isolated test DB; client detects updates without reload, retains focus, and does not unpin the checkpoint. |
| VS5-09 | Server restart, DB replacement, stale token, disconnected/busy DB and overlapping poll requests cannot silently present stale/incorrect study state as current. |
| VS5-10 | Read-only and HTTP boundary tests: `mode=ro` + `query_only`, no schema migration/writes or write routes; host-origin/CSP/XSS/oversized ID/payload checks; no arbitrary file or external content retrieval. |
| VS5-11 | Bounded/reproducible API: exact documented fields, schema v4 gating, pagination, incomplete/truncation and explicit error semantics; compile-time TS types **and** runtime JSON validation. |

1. Read `AGENTS.md`, `README.md`, `docs/project-charter.md`, `docs/architecture.md`, `docs/interfaces-vs003.md`, `docs/interfaces-vs004.md`, `docs/current-state.md`, this task and [the v5 interface](../docs/interfaces-vs005.md). Verify HEAD and avoid unrelated changes.

3. Implement dedicated read-only DB adapter, explicitly bounded GET API, loopback protections and change detector. Do not import or call write-capable service paths.
4. Connect one-page UI, strict types, runtime JSON validation and local built asset serving. Keep selected/pinned state stable during refresh and errors.
5. Test database integrity before/after reads, malformed requests, concurrency, actual separate-writer updates, restart, older schema and original tests/demos. Document commands/results and reversible assumptions in `docs/current-state.md`.
6. Do not add production research actions, new resource allocation policies, annotations, graph editor, general graph renderer, more APIs or migrations to make the demo look impressive.

## 8. Deferred, explicitly non-normative extensions

Full Research Map and Focus Mode with a general graph library, three full Map/Decisions/Execution lenses, generalized timeline, free-text search, alerts, reports, visual progress scoring, user annotations, task creation, human approval UI, websocket push, remote access, multi-user support, public deployment, plugin integrations, real LLM research judgments and genuine scientific claims.

**Debt consciously accepted:** in v1 the first UI is v4-only; observer uses polling and a small Python HTTP server; checkpoint comparison is limited to existing immutable decisions; no persisted UI state. Cleanup trigger is measured usability/performance/security evidence or a later separately authorized milestone, not speculative architecture.
