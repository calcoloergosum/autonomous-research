# VS-002 — Offline planner proposal boundary

**Status:** Approved for implementation by the human project owner (2026-11-10).  
**Prerequisite:** VS-001 complete.  
**Architectural choices:** B / B / A / A, ratified as ADR-012–015 in `docs/decisions.md`.  
**Implementation scope:** Local, deterministic, one host, one study per DB. Do not perform real research or live provider calls.

## Outcome

Prove a durable, permission-separated end-to-end path:

```text
VS-001 study/task/run/evidence state
    -> versioned, reproducible context snapshot
    -> deterministic mock planner response
    -> validated, persisted proposal (NOT a task)
    -> explicit trusted local operator decision
    -> transactionally authorized task import (NOT execution)
    -> existing run-next fixed demo worker
```

The operator can also inspect persisted subordinate question/hypothesis notes and `no_action` records, which never turn into tasks or evidence. The research charter and previous evidence/run history must remain unchanged.

## Authority and safety

- The agent/planner only receives a controller-built context and returns *untrusted bytes*. It has no Store/DB handle, write authority, execution/tool privileges, credentials, network, or permission-change API.
- The selected study's charter, question, success criteria, constraints, source bytes and hash remain immutable. A model's instruction in any description or note is data only.
- A validated task candidate is not executable authority. Only an explicit local operator approval plus a trusted import step can create a pending allowlisted task; the existing `run-next` command must be invoked separately.
- Approval binds to the *exact* proposal content/hash, charter/context hash, local policy identity/version, and locally asserted operator name. This is a local, trusted-operator demo, NOT authenticated human identity. The agent cannot manufacture approval fields.
- Keep the authorization decision behind a distinct trusted interface, so later policy-based authorization could be added without giving the planner the ability to authorize itself. Do NOT implement automatic approval in this slice.
- Existing fixed `demo_mean` worker is the only permitted executable task kind; no generated code, shell, external URLs as execution targets, live LLM APIs, new models, SDK installation, external spending, or network calls.

## A. Database and migration (approved Option B)

Implement **SQLite schema version 2** with append-only/versioned records sufficient for:
1. Canonical context snapshots (including bytes, hash, export schema version, study/charter binding).
2. Planner requests (stable request ID, pinned context, mock/provider and prompt-template identity/version, lifecycle).
3. Raw mock responses / validated proposals (response hash, immutable envelope/content hash, diagnostics for bounded invalid output).
4. Explicit approval/rejection records (operator identifier, policy version/hash, exact content binding).
5. Transactional import receipts (approved proposal -> created task, spec hash, timestamp).

Internal table names are implementation details. Database constraints must enforce uniqueness and relevant foreign keys. Avoid introducing `proposed` into the existing task state machine. Completed planning records and decisions must not be overwritten, and evidence cannot be promoted by the planner.

Migration rules:
- Introduce a deliberate command `python -m arf plan migrate --db PATH` for schema v1 -> v2. It must be transactional and idempotent, and never silently change an unknown/unrelated DB.
- VS-001 `init` may continue creating schema v1; use explicit migration for planning. All VS-001 commands must continue to read and operate on a migrated v2 DB unchanged.
- Preserve the exact study charter bytes/hash, tasks, dependencies, historical runs/costs/evidence, row identities, and pre-existing observations through migration. Test from a populated v1 DB.
- Unknown schema versions must fail without writes. Interrupted migration must roll back. A successful task import and its receipt must commit in **one** SQLite transaction; refactor existing `Store.add_task` internals minimally to share that transaction without nested-BEGIN errors.
- A matching pre-existing task created by another path must never be treated as proof of a successful planner import.

## B. Operator CLI (approved Option B)

Add these explicit commands while keeping every VS-001 command, argument, JSON contract, and error behavior intact:

```bash
python -m arf plan migrate --db PATH
python -m arf plan export --db PATH
python -m arf plan propose --db PATH --context HASH --request-id ID --fixture task
python -m arf plan propose --db PATH --context HASH --request-id ID --fixture note
python -m arf plan propose --db PATH --context HASH --request-id ID --fixture no_action
python -m arf plan list --db PATH
python -m arf plan show --db PATH --id PROPOSAL_ID
python -m arf plan decide --db PATH --id PROPOSAL_ID --decision approve --operator TEXT
python -m arf plan decide --db PATH --id PROPOSAL_ID --decision reject --operator TEXT
python -m arf plan import --db PATH --id PROPOSAL_ID
```

Command names and the `plan` prefix are **VS-002-specific, reversible defaults** necessary to test the approved CLI direction. They are new surfaces with no existing consumers; document exact JSON response keys, error codes and sample invocations in `docs/interfaces-vs002.md` before writing service code. If a necessary change would affect existing public interfaces or permission meaning, stop for review.

Required command behavior:
- `plan export`: persist a complete, consistently ordered, deterministic single-study context and return its SHA-256. Snapshot identity excludes export timestamp and planner bookkeeping tables.
- `plan propose`: accept a stored context hash and stable request ID; use only the named deterministic mock fixture, validate and persist response and proposal, never insert tasks. Repeating an identical completed request returns the persisted result without invoking the mock again. Conflicting reuse of an ID must fail.
- `plan list/show`: expose proposals/notes/no-action plus links to provenance and decisions; clearly label evidence as `unvalidated`.
- `plan decide`: approve/reject only a valid `task_candidate` (notes/no-action remain inert); on approval require current state hash to match captured context. Operator identity is a local assertion. A conflicting/repeated decision cannot rewrite history. Rejection never authorizes import.
- `plan import`: insert one approved task candidate and a receipt atomically after checking exact binding, unchanged context state, policy, allowlist, dependencies and task collisions. Import never triggers `run-next`. Repeating a previously successful import returns its receipt **before** rechecking freshness, even after the imported task ran.
- All errors must be useful on stderr and nonzero; list/show JSON outputs must be stable. Do not use command strings or eval from planner content.

## C. Provider response and proposal contract

Use one action per mock invocation. Trusted controller assigns proposal/request identity and study/charter/context hashes; mock/provider output may contain only:
- `rationale`: bounded, nonempty text
- `evidence_refs`: IDs from the pinned context, unique, possibly empty
- `action`: strict tagged union below.

Action variants:
- `{"type":"task_candidate","task_spec":{...}}`: exactly the current normalized `TaskSpec` fields; only `demo_mean` with finite number input and already-existing dependencies; no executable commands or references to other unimported proposals.
- `{"type":"research_note","note_kind":"question","text":"..."}` or `note_kind="hypothesis"`: durable, inert proposal; no worker, task status or evidence.
- `{"type":"no_action","reason":"..."}`: persistent record that no permitted action is appropriate; no task.

Envelope includes integer `proposal_version=1`, controller-owned `proposal_id`, study ID, charter SHA-256, context SHA-256, rationale, evidence refs and action. Unsupported versions, duplicate JSON keys, extra fields, NaN/Infinity and invalid tagged unions are rejected without writes to the execution queue. Sanitize and bound invalid-response diagnostics; never persist an invalid proposal as valid.

Keep raw response bytes/hash, mock name/version, prompt template bytes/hash or stable template artifact reference, policy version/hash, and controller-observed timestamps separate from claims about scientific validity. Unknown usage must remain unknown; do not fabricate provider costs.

Use deterministic canonical JSON: UTF-8, sorted keys, compact separators, no NaN/Infinity, normalization of optional `TaskSpec` defaults, sorted dependency/evidence reference sets, and preserve input numeric-list order. Record canonicalization/export version. Proposal identity and action-duplicate detection must not be bypassed by changing the rationale. Different request IDs can link to the same valid content without rewriting existing proposal history; distinct task IDs are not assumed scientifically equivalent.

Initial **reversible local limits**: context <= 1 MiB; provider raw response <= 64 KiB; each text field <= 4 KiB UTF-8; each dependency/evidence list <= 64 elements; enforce finite max nesting depth before deep parsing. Reject oversized exports explicitly; do not silently summarize or drop evidence. These limits are not a permanent research policy.

## D. Context and strict freshness (approved Option A)

Export from one consistent SQLite read transaction, stable ordering. Include imported charter source/hash and parsed criteria, tasks and dependencies/statuses, run outcomes and observed costs (preserve null versus zero), evidence IDs/provenance and validation labels. Exclude secrets, environment variables, files outside the DB, chat history, unrelated studies, and planner-internal tables from semantic context identity. Record export version and hash of *exact canonical bytes*.

At first approval and first import, compare current semantic execution-state hash to the stored proposal context hash inside a transaction; if changed, return an explicit stale conflict and require a new context/proposal/approval. Reimporting an existing committed receipt takes precedence over freshness. This conservative policy is intentionally provisional for concurrent future research.

## E. Deterministic mock and test seam

Design an internal protocol similar to `propose(request) -> response bytes + provider metadata`. Use only a deterministic versioned fixture mock keyed by request/context/fixture. Do not call a network endpoint or read credentials.

Mock should cover task candidate, question/hypothesis note, no-action and controlled invalid replies. An interrupted/unknown mock request must not be silently repeated when the outcome is uncertain; persist a review-required state. This does not alter VS-001 run recovery.

## F. Required acceptance tests

- **B1 Migration:** v1 -> v2 on populated DB without changing study/question/source hash, tasks, dependencies, runs, costs or evidence; second migrate is no-op; unknown version and simulated interrupted migration do not corrupt data.
- **B2 Context:** deterministic canonical export hash, original charter bytes and exact evidence labels; planner bookkeeping does not change semantic state hash; oversized export fails visibly.
- **B3 Proposal:** mock task response becomes a persisted proposal, not a task; no active run/evidence; request replay after restart idempotent.
- **B4 Authorization/import:** without approval import denied; an approved exact proposal imports one pending demo task atomically, no execution until separate `run-next`; after run evidence is still unvalidated.
- **B5 Staleness:** intervening task/run/evidence change blocks first approval/import; repeated import with committed receipt succeeds without duplication even if execution changed the current state.
- **B6 Bad inputs:** invalid JSON/fields/refs/hashes, forged approval, prohibited worker kinds, code/commands/URL fields and notes-as-tasks cannot cross into execution.
- **B7 Dedup/concurrency:** duplicate request/proposal/action and import attempts do not cause duplicate tasks; unrelated/manual task ID collision is not silently adopted; concurrent importer is safe.
- **B8 Notes:** subordinate question/hypothesis and no-action responses persist across restarts but cannot become tasks/evidence.
- **B9 Regression:** all VS-001 acceptance tests remain valid after migration; run documented CLI demo with separate processes. Report exact test numbers/commands and limitations, not assumed outcomes.

## Out of scope and stop conditions

No live LLM/Codex SDK connection, provider network, generated-code execution, autonomous feedback loop, per-task science impact/cost model, resource scheduler, exploration/exploitation policy, baseline revision, GPU workers, human queue, approvals by policy, strong operator authentication, multi-host support, automatic recovery/retry, or scientific evidence promotion.

The four B/B/A/A choices are approved. Other defaults in this task are the smallest local, testable additions and must be documented as such. If implementation reveals a material problem involving the CLI/data contract, authorization ownership, migration safety, or security boundary, **stop and present alternatives** rather than silently changing semantics.

When complete: update `README.md`, `docs/current-state.md`, `docs/interfaces-vs002.md` and focused tests. Preserve old fixtures and charter. Run tests, real offline CLI workflow, and `git diff --check`. Do not claim research progress from a plumbing demo.
